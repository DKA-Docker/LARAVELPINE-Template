## 3. Directory Structure & Hierarchy

### Backend Logic (`app/`)
The project follows a **Domain-Driven-like** or **Modular** structure within the standard Laravel `app` directory.
- **Controllers**: `app/Http/Controllers/V1/Frontend/Dashboards/Apps/...`
  - Logic is deeply nested to match the UI navigation structure (e.g., `Deliveries/Requests`).
  - Controllers are lightweight, primarily returning Views.
- **Livewire**: `app/Livewire/Metronic/...`
  - Reactive components are namespaced under `Metronic`.
  - Follows the same hierarchy as Controllers/Views where possible.
- **Jobs/Mails**: Organized similarly (e.g., `app/Mail/Dashboards/Apps/...`).

### Frontend & Views (`resources/`)
**Critical Pattern**: The standard `resources/views` directory is **NOT** the primary location for application pages.
- **Views Location**: `resources/layouts/metronic/`
  - Configured in `config/view.php` via `config('theme.name')`.
  - Example: `view('dashboards.index')` -> `resources/layouts/metronic/dashboards/index.blade.php`.
- **Assets**: `resources/theme/metronic/`
  - Contains raw JS (TypeScript), CSS, and Vendor assets.
  - Built via Vite.

### Database & Migrations (`database/migrations/`)
**Critical Pattern**: Migrations are **MODULAR**, not a single flat list.
- `accounts/`: User and Auth related tables.
- `apps/`: Core application logic tables (Deliveries, etc.).
- `data/`: Reference data / Lookups.
- `sys/`: System level tables (Jobs, Failed Jobs, etc.).
- **Rule**: When creating migrations, place them in the correct subdirectory based on domain.

### Storage & Files (`storage/app/`)
- Contains sensitive keys like `firebase-auth.json`.
- **Mount**: Mapped via Docker volume `storage-data`.

### Bootstrap & Middleware (`bootstrap/app.php`)
- **Middleware**:
  - `SetLocale`: Applied to `web` group.
  - `Authenticate`: Aliased as `auth`.
  - `JSONCheckRequest`: Applied to `Api` group.

### Configuration (`config/`)
- `theme.php`: Controls the active theme (default: `metronic`).
- `view.php`: dynamically maps view paths based on the theme.

## 7. Project Rules & Conventions
> [!WARNING]
> **STRICT ADHERENCE REQUIRED.** Do not deviate from these patterns.

### 7.1. Directory & Class Naming
- **Models**:
  - **Path**: `app/Models/[Module]/[SubModule]/[Feature]/[ClassName].php`
  - **Convention**: `ClassName` = Concatenation of directory path (e.g., `AppsDeliveriesRequests`).
  - **Traits**: `HasFactory`, `SoftDeletes`.
  - **Keys**: `public $incrementing = false;`, `protected $keyType = 'string';`.
- **Repositories**:
  - **Path**: `app/Repositories/[Module]/[SubModule]/[Feature]/`
  - **Pattern**: `[Feature]RepositoryInterface.php` adjacent to `[Feature]Repository.php`.
- **Controllers**:
  - **Path**: `app/Http/Controllers/V1/Frontend/[Module]/[SubModule]/...`
  - **Nesting**: Must match the UI breadcrumbs and Route prefixes exactly.

### 7.2. Routing (routes/web.php)
- **Grouping**: Use deeply nested `prefix()` and `name()` groups to mirror the controller structure.
- **Resources**: Use `Route::resource('/', Controller::class)` inside the final group.
- **Naming**: e.g., `dashboards.apps.deliveries.requests.index`.

### 7.3. Views
- **Location**: `resources/layouts/metronic/[module]/...`
- **Config**: Do not use `resources/views` directly. Custom config in `config/view.php` handles this.

## 8. Functional Concepts
### Core Domains
- **Accounts**: Authentication, User Management, Roles.
- **Apps**:
  - **Deliveries**: 
    - **Requests**: Handling delivery orders/requests (UUID based).
    - **Tasks**: Assignments related to requests.
    - **Tracking**: Real-time monitoring of deliveries.
  - **Logistics**: (Implied) Fleet and Asset management.
- **Data**: Master data management (Destinations, Packages).
- **Sys**: System-level configurations (Jobs, Queues).

### Business Logic Flow
- **Entry**: Web Routes -> Deeply Nested Controllers.
- **Logic**: Controller -> Service (if complex) OR Repository -> Model.
- **Output**: View (Blade in `resources/layouts/metronic`) or JSON (API).

## 9. Micro-Architecture Rules (Advanced)

### 9.1. Service Layer Pattern (`app/Services`)
- **Instantiation**: Manual instantiation of Repositories in `__construct`. No Dependency Injection.
- **Transactions**: STRICT manual `DB::beginTransaction()`, `commit()`, `rollBack()`.
- **Response Format**: STRICT Standardized array output:
  ```php
  return [
      'status' => true,        // boolean
      'code'   => 200,         // integer HTTP-like code
      'msg'    => 'Success',   // string user-friendly message
      'data'   => $model,      // mixed data
      'error'  => null         // optional detail
  ];
  ```
- **UUIDs**: Generate UUIDs manually (`Str::uuid()`) *before* calling Repository Create.
- **Mass Assignment**: Clean payloads (`unset`) manually before passing to localized repositories.

### 9.2. Validation & Error Handling
- **Strategy**: **Implicit / Database-Driven**.
  - No `FormRequest` or `$this->validate()` observed in core logic.
  - Relies on Database Constraints (Not Null, Foreign Key) to throw Exceptions.
  - Service catches `Throwable`, rolls back DB, and returns `status => false` with error message.
- **Helpers**: `app/Helpers/Exceptions/` available for specific HTTP Codes (if needed).

#### 9.3. Livewire Patterns
- **Attributes**:
  - `#[Lazy]`: Used on full-page components for performance.
  - `#[Modelable]`: Used on child components to sync data (e.g., `ItemsLayout`).
- **Authorization**:
  - **Inline**: `Auth::user()->can(...)` in `mount()`.
  - **Blocking**: Set `$this->isAuthorized = false` and return `unauthorized` view in `render()`.
- **Logic**: minimal logic. Delegates heavy lifting to Services.

### 9.4. Repository Pattern (`app/Repositories`)
- **Responsibility**: Strictly for data access and constructing Query Builders.
- **Prohibited**: Do **NOT** place Business Logic (e.g., complex filtering, conditional constraints based on business rules) in Repositories.
- **Pass-through**: If logic/filtering is needed, generic methods (like `whereIn`) are acceptable, OR return `query()`/`Builder` to the Service and apply specific business logic there.
- **Rule of Thumb**: "Repository gets data, Service decides what data to get."

## 10. Asynchronous & Tooling Layer

### 10.1. Mails & Notifications
- **Pattern**: **Queued Job Dispatch**.
  - NEVER send mails directly from Controller/Service.
  - **Flow**: Service -> `Dispatchable` Job -> `Mailable`.
  - **Job Config**: `$tries = 3`, `$backoff = 10` (Standard).
  - **Namespace**: `App\Mail\Dashboards\Apps\...` (Match Module Structure).

### 10.2. Console & Dev Tooling (`app/Console/Commands`)
- **Custom Commands**: Extensive custom wrappers for Docker & Deployment.
  - `DockerComposeUp`, `DockerComposePull`, `ProjectMigrate`.
  - **Usage**: Prefer these over raw `docker compose` commands when possible as they handle env vars and paths.

### 10.3. Realtime (Reverb)
- **Config**: `routes/channels.php`.
- **Driver**: Reverb (WebSocket).
- **Channels**: Private channels scoped by User ID pattern: `App.Models.User.{id}`.

## 11. Database & Deep Migration Rules
> [!IMPORTANT]
> **World-Class Research Level Depth**: The migration system is highly customized.

### 11.1. Hierarchy & Loading
- **Recursive Loading**: `AppServiceProvider::boot()` explicitly loads **ALL** subdirectories in `database/migrations/`.
  - logic: `File::allDirectories(database_path('migrations'))`.
- **Structure**:
  - `database/migrations/apps/deliveries/requests/` (Deeply nested).
  - `database/migrations/accounts/` (Domain roots).

### 11.2. Table Naming Convention
- **Rule**: Table name **MUST** match the directory path structure (snake_case).
  - Path: `apps/deliveries/requests/`
  - Table: `apps_deliveries_requests`
- **Violation**: Creating a table `requests` inside nested folders is **FORBIDDEN**.

### 11.3. Schema Standards
- **Primary Key**: UUID (`$table->uuid('id')->primary()`).
- **Foreign Keys**: `foreignUuid('account')` constrained to `accounts`.
- **Traits**: Always include `$table->softDeletes()` and `$table->timestamps()`.
- **Comments**: Every column must have a comment explaining its purpose (`->comment("Adalah Judul...")`).

## 12. Generative Scaffolding Rules
> [!TIP]
> **Use this when asked to "Create a new Module" or "New Feature".**

#### 12.1. When Creating a New Module Folder (e.g., `Apps/NewFeature`)
You must generate the following **Minimum Viable Trio**:
1.  **Model**: `app/Models/Apps/NewFeature/AppsNewFeature.php`
    - Class Name: `AppsNewFeature` (Concatenated Path)
    - Extends `Model`
2.  **Repository Interface**: `app/Repositories/Apps/NewFeature/NewFeatureRepositoryInterface.php`
    - Namespace: `App\Repositories\Apps\NewFeature`
3.  **Repository Implementation**: `app/Repositories/Apps/NewFeature/NewFeatureRepository.php`
    - Implements Interface.
    - Namespace: `App\Repositories\Apps\NewFeature`

#### 12.2. When Creating a Controller
1.  **Path**: `app/Http/Controllers/V1/Frontend/Dashboards/Apps/NewFeature/Index.php`
2.  **Service**: MUST instantiate a Service, which instantiates the Repository.
3.  **Route**: Register in `routes/web.php` under `dashboards.apps.newfeature`.

#### 12.3. When Creating a Migration
1.  **Path**: `database/migrations/apps/new_feature/` (Snake Case Folder)
2.  **Filename**: `YYYY_MM_DD_HHMMSS_create_apps_new_feature_table.php`
3.  **Table Name**: `apps_new_feature`

## 13. Clean Code & Aesthetics
> [!TIP]
> **"Zero Config" Philosophy**: The architecture depends on naming purity.

### 13.1. Models (No `$table`)
- **Prohibited**: Do NOT define `protected $table = '...'`.
- **Mechanism**: The class name `AppsDeliveriesRequests` automatically resolves to snake_case `apps_deliveries_requests`.
- **Constraint**: This ONLY works if you strictly follow the **Directory Naming** rules (camelCase Class = snake_case Table).

### 13.2. Factories (No `$model`)
- **Prohibited**: Do NOT define `protected $model = ...`.
- **Mechanism**: Namespace alignment enables Laravel to guess the model.
- **Path**: `Database\Factories\Apps\...` matches `App\Models\Apps\...`.

### 13.3. Clean Inputs
- **Code**: `public $incrementing = false;` is the only "noise" allowed in Models (due to UUIDs).
- **Validation**: Keep it out of Controllers/Models. Push it to Services (Implicit) or Livewire (Explicit Logic).

## 14. Deep Frontend & Asset Ecosystem

### 14.1. Blade & Livewire Coupling
- **Attributes**: Heavy use of `wire:model.defer` for performance.
- **Keys**: `wire:key` is MANDATORY for all loops (`wire:key="packages-{{ $index }}"`).
- **Nesting**: Blade files are deeply nested to match Controller structure (`creates/destinations/packages/...`).
- **Partials**: Prefer Blade `@include` or Livewire Child Components over complex custom `<x-components>`.

### 14.2. TypeScript Architecture (`resources/theme/metronic/js`)
- **Coupling**: TS manipulates Livewire state explicitly.
  - Pattern: `Livewire.find(componentId).set('property', value)`.
  - Usage: Complex UI interactions (Maps, Charts) that Livewire can't handle natively.
- **Modules**: Separate TS files per Page/Feature (e.g., `requests/create.ts`).
- **Managers**: Use "Manager" objects (e.g., `DestinationMapManager`) to handle dynamic instances (repeater fields).
- **Global Object**: `window.Livewire` is used to bridge the gap.

### 14.3. Asset Build System
- **Proxying**: JS uses internal proxies (e.g., `geocoding-proxy`) to avoid exposing API Keys or CORS issues.
- **Theme Observer**: JS listens to `dark` mode class changes on `<html>` to update 3rd party libs (Mapbox styles).

### 14.4. Strict Execution Guard (The "Lock" Rule)
- **Concept**: Since assets are bundled globally, TS files must **NOT** execute logic unless they are on the correct page.
- **Mechanism**:
  - **Blade**: Must include a unique wrapper class (e.g., `<div class="request-create-destinations-wrapper">`).
  - **TypeScript**: Must start with a "Lock Check":
    ```typescript
    if ($('.request-create-destinations-wrapper').length === 0) return;
    ```
- **Constraint**: This is a **Strict Architectural Rule**. JS without this guard is considered **Unsafe**.
## 15. Resource Organization & Build Pipeline
> [!NOTE]
> **Dynamic Build System**: Vite is configured to scan themes automatically.

### 15.1. Directory Hierarchy
- **`resources/layouts/[theme]/`**: Contains **Blade Templates**.
  - `dashboards/`: Application pages.
  - `components/`: Reusable UI chunks.
- **`resources/theme/[theme]/`**: Contains **Raw Assets** (TS, CSS, Images).
  - `js/`: TypeScript entry points.
  - `css/`: Tailwind/CSS entry points.

### 15.2. Build Configuration (`vite.config.ts`)
- **Auto-Discovery**:
  - Scans `resources/theme/*` directories.
  - Automatically adds `css/app.css`, `js/app.ts`, or `js/app.js` as entry points.
- **Plugins**:
  - `laravel-vite-plugin`: Hot Module Replacement (HMR).
  - `@tailwindcss/vite`: v4.0 integration.
  - `vite-plugin-javascript-obfuscator`: Code protection in build mode.
  - `vite-plugin-compression`: Brotli compression (`.dka` ext).

### 15.3. Layout & View Resolution
- **Config**: `config/view.php` dynamically sets paths based on `theme.name`.
- **Usage**: `return view('dashboards.index')` resolves to `resources/layouts/[theme]/dashboards/index.blade.php`.
